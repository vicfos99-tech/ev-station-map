- **T1** Q1(지도 탭의 길 위 풍선). 잠긴 통합 흐름은 '경로' 탭을 거친 뒤만 본다.
- **T2** 통합 흐름 s3~s9 가 참조 출력과의 대조라는 것(G3). 참조와 제품이 함께 틀리면 통과한다 — Q1·Q3 이 그 예다.
- **T3 navi(길찾기) 노선에서 '새로 받기'.** `routeKey` 가 `navi` 면 `extraIds` 로만 받는데 이 길은 통합 흐름에 없다(이 세션도 돌리지 못함). 길 위 휴게소가 `routes.json` 에 하나도 없으면 첫 노선의 상태를 받는다(`wantedIds` 규칙).
- **T4 상태를 충전기에 붙이는 자리(N4).** `routes.json` 충전기에 id 가 없어 `chgerId` 순으로 앞에서부터 붙인다. 탐침 F: 100kW·200kW 급속 둘에 `01`=충전 중·`02`=대기를 주면 `100kW:charging, 200kW:available`. 중계가 `routes.json` 충전기를 `chgerId` 순으로 적지 않았다면 빈자리 **수**는 맞아도 어느 출력이 비었는지가 뒤바뀐다. 급속·완속이 섞인 충전소는 통째로 미확인이다.
- **T5 실제 중계 파일과의 맞물림(M1~M3).** `routes.json` 의 노선 key·휴게소 충전소 id 가 폰의 `live.js` 와 같은지, `status/rest/<id>.json` 이름이 그 id 인지, 모든 시군구가 올라오는지, GitHub Pages 캐시·CORS·안드로이드 웹뷰. 나들목 항목은 옛 자료에서 노선 key 로 맞춰 옮기므로 key 가 다르면 나들목이 사라진다(코드 읽기, `app.js` 965~975행).
- **T6 폰 시계.** 느리면 낡은 상태를 새 것으로 본다(M7). 5분 넘게 빠르면 반대로 치우친다: 탐침 F 에서 폰이 29분 빠르면 방금 확인된 상태(09:10)가 `31분 전 상태라 빈자리를 세지 않았어요` 가 된다.
- **T7 지도 안내 글 한 칸을 여러 시군구가 나눠 쓴다(코드 읽기).** 뒤에 읽은 시군구의 note 가 비면 앞 시군구의 "N분 전 상태예요" 같은 글을 지운다. 풍선의 수는 시군구마다 따로 맞게 세어진다.
- **T8 판정이 알고 둔 테스트 빈틈.** r1(`saveBase` 가 검사 전에 `getItem` 을 불러도 통과), r3(`parseStations` 의 느슨한 `v`, 안쪽 객체의 프로토타입), r4(`oldest`, `onProgress` 없는 성공 갈래), r5(요금표 칸 이름이 `constructor` 같은 것일 때). 제품 코드는 A10 처럼 맞게 돼 있으나, 뒤에 누가 고치면 테스트가 알려 주지 않는다.
- **T9 CI.** `.github/workflows/ci.yml` 은 잠금 확인과 pytest 뿐이고 JS 대조 단계는 없다(계획 2.0-7). 기존 대조는 pytest 안의 `test_build` 가 대신 돌린다. 새 테스트는 node 가 있어야 하고, `web/test/navi_fixture.json` 은 저장소에 없어 다른 PC·CI 에서는 `compare_navi.js` 를 건너뛴다.
- **T10 고른 노선만 받는다(N3).** `routes.json` 은 하루 한 번쯤 다시 쓰이므로, 중계로 받은 뒤 다른 노선은 거의 늘 30분 규칙에 걸려 전부 미확인으로 보인다(빈자리를 부풀리지는 않는다). 노선을 바꾸면 안내 글이 뜬다.

## 5. 묘성이 정해야 할 것

1. **D1 Q1 을 고칠지.** 권고: 배포 전에 고친다(요구사항 한 줄로 지휘 스크립트에). 지도 탭이 운전 중 화면이라 원칙 2 가 가장 필요한 자리다. Q3(의심 지역 안내 유지)·Q6(키 가리기 넓히기)·Q7(안내 글)·G5-①(낡은 주석)도 작으니 같은 실행에 묶을 수 있다.
2. **D2 오래됨을 재는 기준 시각(N1, 계획 2.0-1).** 요구사항 글자("상태 파일의 `at`")대로면 조용한 충전소가 30분 뒤 전부 미확인이 되고, 지금 구현(`meta.json` 이 보증)이면 Q2 처럼 중계의 `ok`·`fresh` 를 믿는다. 지금대로 두려면 중계가 "일부 지역만 실패한 차례"에 `ok` 를 어떻게 두는지 확인하고, 휴게소 파일에도 지역 확인을 넣을지 정한다.
3. **D3 ⚠ 15분(안내)·30분(세지 않음)·3분(지도 상태 다시 읽기).** `relay.js` 의 `NOTE_MIN`·`DROP_MIN`, `app.js` 의 `AR_STATUS_MIN`. 중계가 10분마다 올리면 한 번 걸러도(20분) 안내만 뜨고 세 번 거르면 세지 않는다.
4. **D4 올리는 순서.** `master` 에 push 하면 `pages.yml` 이 바로 빌드해 올리고, 중계는 기본 켬이다. 그때 사이트에 `relay/` 폴더가 아직 없으면: 키 없는 사람은 `중계에 파일이 없어요. 공공 데이터 키를 넣으면 직접 받을 수 있어요.`(탐침 E), 키 있는 사람은 누를 때마다 중계 실패 뒤 직접 받기와 "중계에 연결하지 못해 직접 받았어요". 그러니 ① `pages.yml` 이 `relay-data` 브랜치를 `_site/relay/` 에 넣게 고치고 중계가 실제로 올리는 것을 본 뒤 ② 앱을 push 한다. 안드로이드 앱은 `app/copy-web.js`·`app/build-apk.sh` 로 다시 만들어야 중계가 들어간다. `web/dist/` 세 파일을 저장소에 다시 만들어 넣을지도 함께.
5. **D5 중계 `routes.json` 충전기에 id 를 넣을지(N4, T4).** 넣으면 섞인 충전소의 미확인과 출력 뒤바뀜이 함께 풀린다(중계 쪽 수정).
6. **D6 노선을 바꿀 때 저절로 받을지(N3, T10).** 지금은 안내 글만 뜨고 '새로 받기'를 눌러야 한다.
7. **D7 '상태 미확인'을 화면에 어떻게 보일지(N13).** 지금은 기존 stat 9 와 같이 '고장·점검'으로 센다. 30분 넘은 것이 모두 고장처럼 보인다.
8. **D8 통합 테스트 꼴(G3·G4).** 새 글 3000자 한도를 계속 둘지, 기대값을 참조 출력이 아니라 계획서 글에서 따로 적게 할지.

## 7. 실제 폰에서 확인할 것

1. 중계 주소로 실제로 읽히는지(웹은 `./relay/`, 안드로이드 앱 안은 상수 주소. Pages 캐시 10분·CORS).

6. 실제 `routes.json` 으로 받은 뒤 나들목 인근 충전소가 그대로 남는지(T5), 출력이 다른 충전기가 있는 휴게소의 빈자리가 맞는 충전기에 붙는지(T4).
